Multi-Tenant RBAC Plan

TextileIQ — Tenant isolation, role-based access, Gmail/WhatsApp sharing by owner

What's Wrong Today

1. Gmail appears connected for every new user — IntegrationConfig is scoped to tenantId, not to a specific user. Any new user in the same tenant immediately sees the owner's Gmail as "connected" — this is actually correct data-sharing behaviour, but the UI doesn't gate who can change it.

2. No real RBAC on API routes — requireRole middleware exists but is only applied to a few integration routes. Any logged-in user (STAFF, READONLY) can call POST /api/v1/inventory, DELETE /api/v1/parties/:id, etc.

3. No UI permission gating — buttons like Add Product, Delete Party, Configure Gmail are shown to all roles regardless.

How Tenancy Already Works (No Schema Change Needed)

The schema already has everything needed:

  • Tenant = the company (e.g. "Sharma Textiles Pvt Ltd"). One per customer.
  • Group = optional sub-division within a tenant (e.g. "Wholesale Team", "Retail Branch"). Optional — most small companies won't use it.
  • User → belongs to a Tenant, optionally to a Group. Has a role field (OWNER | MANAGER | ACCOUNTANT | STAFF | READONLY).
  • IntegrationConfig → scoped to tenantId. One Gmail config per tenant. All users of that tenant share it automatically. Only OWNER can modify it.

✅ Gmail/WhatsApp sharing is already correct at the data layer. The fix is purely access control: only the tenant OWNER can connect/disconnect/reconfigure integrations. All other roles see status (connected/not connected) but cannot change it.

Implementation Phases

1

Phase 1 — Backend Permission Middleware

Create a requirePermission(action) middleware that reads req.user.role from the JWT and checks against a permissions map. Apply it to every mutating route (POST, PUT, DELETE). No schema change. Touch: src/backend/src/middleware/permissions.ts (new file) + all 6 route files.

2

Phase 2 — Integration Routes: Owner-Only Gate

Lock POST /api/v1/integrations/gmail/connect, /disconnect, /whatsapp/connect etc. to OWNER role only. All other roles can GET status but cannot POST/DELETE. Touch: integrations.ts.

3

Phase 3 — Return role in JWT / /me endpoint

Ensure role is included in the JWT payload and in the GET /api/v1/auth/me response. The frontend needs it to gate UI. Touch: auth.ts route + authMiddleware.ts.

4

Phase 4 — Frontend Permission Hook

Add a usePermissions() hook that reads role from auth context and exposes boolean helpers: canEdit, canDelete, canConfigureIntegrations, etc. Touch: src/frontend/src/hooks/usePermissions.ts (new).

5

Phase 5 — Gate UI buttons by role

Use usePermissions() in each page to conditionally render Add/Edit/Delete buttons and the Settings → Integrations section. Touch: InventoryPage, SalesPage, PartiesPage, LeadsPage, SettingsPage.

6

Phase 6 — User Management UI (Settings)

Add a "Team" tab to Settings where OWNER/MANAGER can invite users, assign roles, activate/deactivate. Backend: GET/POST/PUT/DELETE /api/v1/users (scoped to tenantId). Touch: SettingsPage.tsx + new users.ts route.

What Stays the Same

  • No schema changes needed — UserRole enum and IntegrationConfig.tenantId are already correct.
  • Data isolation is already correct — every query is already scoped by tenantId.
  • Gmail tokens are already per-tenant — all users of a tenant already see the same connected Gmail. Just need to hide the Connect/Disconnect button from non-OWNER roles.
  • No migration needed — the role column already exists on users.

Recommended Build Order

  1. Phase 1 + 2 together — backend permissions middleware + owner-only integration gates (one PR)
  2. Phase 3 — role in JWT/me (small, unblocks frontend)
  3. Phase 4 + 5 together — frontend hook + gate all UI buttons (one PR)
  4. Phase 6 — User management UI (largest, standalone PR)
